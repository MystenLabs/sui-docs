A price oracle brings offchain data, most often an asset price, onchain so a smart contract can act on it. Any DeFi app that values collateral, liquidates a position, prices a swap, or settles a market against a real-world number needs one, because that number does not exist onchain until an oracle publishes it.

The stakes are high: a wrong or stale price can drain a lending pool or liquidate a healthy position. Reading a feed is a few lines; reading it safely is the real work, and it is the subject of this cluster.

## What is the difference between a pull and a push oracle?

Two models put a price onchain, and the difference shapes your integration.

- **Pull (on-demand):** Nobody keeps the onchain price current for you. Your transaction fetches a fresh, signed update offchain, applies it onchain, and reads it, all in one atomic transaction. You pay for the update only when you use it, and the price is as fresh as the moment you transact. On Sui, Pyth works as a pull oracle.
- **Push:** A separate service, a keeper, posts prices to an onchain object on a schedule or when the price moves past a threshold. Consumers read the last posted value. The freshness of a push feed is only as good as the keeper's cadence, so a push consumer must still check how old the stored price is.

The pull model is the default on Sui because it puts freshness in the consumer's control: the update and the read happen together, so a consumer never acts on a price the transaction did not just refresh.

## How does price data live in Sui objects?

On Sui, an oracle price is not a global variable. It lives in a shared object that your transaction references:

Pyth stores each feed in a `PriceInfoObject`. You update that object with a signed price, then read it.

Because the update and the read are commands in the same [programmable transaction block (PTB)](/develop/transactions/ptbs/prog-txn-blocks), a single atomic transaction that runs its commands in order, the object the consumer reads is the one the transaction just refreshed. The order matters: the update command must come before the read. Freshness is a property of a single transaction, not a background guarantee, which is exactly why a consumer checks the price's publish time against the onchain clock.

In outline, a pull integration follows these steps:

1. Offchain, fetch a signed price update from the Hermes service.
2. In your PTB, apply the update to the feed's `PriceInfoObject`.
3. In the same PTB, after the update command, read the price and confirm it is fresh: `pyth::get_price_no_older_than` rejects a price older than the bound you pass.

## Which oracle should I use on Sui? {#should-i-use-pyth-or-switchboard-on-sui}

[Pyth](https://docs.pyth.network/price-feeds/contract-addresses/sui) ships an audited Move package on Sui Mainnet and Testnet, and the pages in this cluster use it. Pyth offers a large catalog of shared price feed IDs that are the same across chains, a staleness gate built into the read (`pyth::get_price_no_older_than`), and the `@pythnetwork/pyth-sui-js` TypeScript package. For other oracle providers, see [Oracles](/getting-started/tooling#oracles) in the tooling directory.

As a concrete reference point, [DeepBook Margin](/onchain-finance/deepbook/deepbook-margin/margin-integration) consumes Pyth `PriceInfoObject`s for its risk math. For custom, non-price data brought onchain through a trusted enclave rather than a price network, see [Nautilus](/sui-stack/nautilus/nautilus-overview).

## What happens when a price is stale

The Pyth staleness check aborts on a stale feed. Move has no try/catch to recover from that abort onchain, and if one transaction command fails, the entire block fails and none of the effects from the commands apply, so the transaction fails instead of returning an old value. Your consumer gets a fresh price or a clear abort, never a silently stale one.

To keep a transaction alive when the primary feed is stale, use a fallback feed:

1. Read the primary feed with the unchecked Pyth reader, `pyth::get_price_unsafe`.
2. Test its freshness yourself, without aborting.
3. If the primary is stale, read a secondary feed with the checked reader, `pyth::get_price_no_older_than`. This read still aborts if the secondary feed is also stale.

In the pull model, the transaction applies the Hermes update before the read. A stale read through a staleness bound means the update did not land, and the read aborts. The [Move Adapter Pattern](move-adapter) implements this fallback.
