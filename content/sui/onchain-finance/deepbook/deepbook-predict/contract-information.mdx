DeepBook Predict runs on Sui Mainnet and Sui Testnet as 2 separate deployments, `deepbook-predict-mainnet` and `deepbook-predict-testnet`. Both run `predict` protocol version 5, `deepbook_predict_orders` protocol version 2, and `sessions` protocol version 4, together with the `deepbook_predict_math`, `propbook`, `account`, and `deepbook_core_account` versions they link, so every trade is a [queued order](/onchain-finance/deepbook/deepbook-predict/contract-information/predict#queued-orders) and the 2 networks expose the same entrypoints. Version TBD-DBU-1166: SDK release or later of [`@mysten/deepbook-v3`](https://www.npmjs.com/package/@mysten/deepbook-v3) returns the identifiers on this page from `getConfig`, as [DeepBook Predict SDK](/onchain-finance/deepbook/deepbook-predict-sdk#client) explains.

The Mainnet publish comes from DeepBookV3 source commit [`7b169bde`](https://github.com/MystenLabs/deepbookv3/tree/7b169bde2c2a25fee3ac9aa4686e346309bfe570/packages/predict), and the original Testnet publish from source commit [`4d752fb8`](https://github.com/MystenLabs/deepbookv3/tree/4d752fb82d909a821c85bcc5d3963725efb546f4/packages/predict), whose Move sources are byte-identical to the Mainnet ones. Both networks then took the same 4 upgrades:

| **Protocol version** | **What it added** | **Source commit** |
| --- | --- | --- |
| 2 | The [`mint_exact_cost`](/onchain-finance/deepbook/deepbook-predict/contract-information/predict#mint-a-position) all-in budget entrypoint and its session wrapper, in `predict` and `sessions` version 2. Protocol version 4 retired both in favor of the `enqueue_exact_cost` queued order. | [`8d7d42a0`](https://github.com/MystenLabs/deepbookv3/tree/8d7d42a0f48bc6434bc282d45d2403809b4e492c/packages/predict) |
| 3 | [`plp::add_usdc_to_plp`](/onchain-finance/deepbook/deepbook-predict/contract-information/vault#add-usdc) | [`abb4cfd9`](https://github.com/MystenLabs/deepbookv3/tree/abb4cfd93b2e51f7925941fe5d53b3fe70fc140c/packages/predict) |
| 4 | Delayed execution: the queued-order flow, `sessions` protocol version 3, and the new `deepbook_predict_orders` and `deepbook_predict_math` packages. The immediate mint and live-redeem entrypoints abort. | [`29117434`](https://github.com/MystenLabs/deepbookv3/tree/2911743402372d3e79ab5d48a0f9ed64f1a32159/packages/predict), with Mainnet built from the byte-identical `98128174` |
| 5 | [Builder fees named on each order](/onchain-finance/deepbook/deepbook-predict/contract-information/predict#builder-fees), [fee bands](/onchain-finance/deepbook/deepbook-predict/design#fee-bands), the admin-managed [cadence table](/onchain-finance/deepbook/deepbook-predict/contract-information/registry#cadence-configuration), narrower entry bands at market creation, and SVI priced at 1e18, together with `deepbook_predict_orders` protocol version 2, `sessions` protocol version 4, and new versions of `propbook`, `deepbook_predict_math`, and `account`. `redeem_settled` and `redeem_settled_permissionless` abort. | [`046ffd1e`](https://github.com/MystenLabs/deepbookv3/tree/046ffd1e2af6ae511146a0fcb92f5eb8a7e843af/packages/predict) |

An integration built for protocol version 4 meets these differences:

- **Builder fees:** An order pays a builder fee only when it names a `BuilderCode` and a fee per contract through a `_with_builder` entrypoint, capped at `builder_fee_cap`. A code attached to the account no longer affects fees, and the account quotes charge no builder fee. See [Name a builder fee](/onchain-finance/deepbook/deepbook-predict/contract-information/predict#builder-fees).
- **Settled redemption:** `redeem_settled`, `redeem_settled_permissionless`, and the Sessions `redeem_settled` wrapper always abort, and the settled-redeem keeper allowlist setters abort with `ESettledRedeemRetired`. See [Redeem a position](/onchain-finance/deepbook/deepbook-predict/contract-information/predict#redeem-a-position).
- **Fees:** A market created after an admin sets fee bands charges a multiple of the trading fee inside them. See [Fee bands](/onchain-finance/deepbook/deepbook-predict/design#fee-bands).
- **Cadences:** Cadence IDs index a table that `registry::add_cadence` can extend past the 6 built-in cadences, so read the periods with `registry::cadence_periods` rather than hardcoding 6. See [Registry](/onchain-finance/deepbook/deepbook-predict/contract-information/registry#cadence-configuration).
- **Entry bands:** A market's entry band can be narrower than the template, so read each market's own band. See [Market creation](/onchain-finance/deepbook/deepbook-predict/contract-information/registry#market-creation).
- **SVI precision:** Predict reads each SVI row at the decimals its Propbook store signs at, 9 or 18. See [Oracle](/onchain-finance/deepbook/deepbook-predict/contract-information/oracle#svi-decimals).
- **Sessions:** A session spot order needs its pool on an admin allowlist, and a session's builder fee needs the account owner's approval. See [Sessions](/onchain-finance/deepbook/deepbook-predict/contract-information/sessions).

Every upgrade kept its original ID, so the lineage is unchanged and every object, position, account, and session grant created before it stays valid.

### Publish count is not protocol version {#version-numbers}

Two different numbers share the name version, and they have come apart. Protocol version decides what a network can do; the publish count only records how many publishes a package has had:

| **Package** | **Publishes** | **Protocol version** |
| --- | --- | --- |
| Mainnet `predict` | 5 | 5 |
| Mainnet `predictOrders` | 2 | 2 |
| Mainnet `sessions` | 4 (TBD-DBU-1166: Mainnet Sessions v4 upgrade) | 4 |
| Testnet `predict` | 10 | 5 |
| Testnet `predictOrders` | 5 | 2 |
| Testnet `sessions` | 9 | 4 |
| `propbook` | 2 on Mainnet, 3 on Testnet | 2 on both networks |
| `predictMath` and `account` | 2 on each network | None. These packages have no version gate |
| `deepbookCoreAccount` | 1 on Mainnet, 2 on Testnet | None. This package has no version gate |

- **Publishes** is what `Published.toml` records: how many publishes that package has had on that network. It only counts events, so a Testnet-only rehearsal of an upgrade leaves Testnet permanently a publish ahead.
- **Protocol version** is `constants::current_version!()`, compiled into the code. It gates behavior: [`assert_version`](#version-gate) aborts unless it is at or above the `ProtocolConfig` watermark, and it is what determines whether an entrypoint exists.

Testnet `predict` is on its 10th publish and Mainnet's on its 5th, yet both run protocol version 5, because Testnet-only rehearsals left Testnet publishes ahead. Compare protocol versions, never publish counts, when you want to know what a network can do.

### The version gate {#version-gate}

Every version-gated call runs `assert_version`, which aborts with `EPackageVersionDisabled` unless `constants::current_version!() >= ProtocolConfig.version_watermark`. An older package therefore keeps working until an admin raises the watermark past it, at which point every call through it stops. That is what makes a stale call target in a client library a deferred failure rather than an immediate one.

Each network's Version 5 cutover raised its watermark to 5, so only protocol version 5 runs on either. `SessionsConfig` has a watermark of its own, raised to 4, so a call through a Sessions package that compiles version 3 or lower aborts with `session_config::EPackageVersionDisabled`, and that includes the DeepBook spot wrappers. `deepbook_predict_orders` has a floor of its own on each `OrderDesk`, raised to 2.

## Upgraded packages carry 2 IDs {#two-ids}

A Move package upgrade publishes at a new address and keeps its original one. The 2 IDs are not interchangeable, and both networks need both:

- **Call target:** the latest published address. Every `moveCall` target, and every `Auth` or capability argument resolved against the package, uses it.
- **Original ID:** the address of the package's first publish. Every type tag keeps it forever, so struct types, event type prefixes, the PLP coin type, and dynamic-field keys all derive from the original ID, never from the call target.

A type that a later version introduced is the exception: its type tag carries the defining ID of the version that introduced it. The types and events that protocol version 4 added to `predict`, such as `config_events::OrderFlowUpdated`, carry the address of the `predict` version that introduced them: the Testnet version 5 address `0x0654ecbe…` and the Mainnet version 4 address `0x98235c58…`. The types that protocol version 5 added, such as `config_events::FeeBandsUpdated`, carry the Mainnet version 5 call target, `0xb0aaafe0…`, while Testnet introduced them across several rehearsal publishes. The version numbers do not line up across networks, so check the defining ID on each one.

The SDK carries both: `packages.predict` and `sessionsPackageId` are the call targets, `packages.predictV1` and `sessionsPackageIdV1` the original IDs, and `packages.predictDelayedExecution` is the `predict` version that defines the delayed-execution types. A Mainnet integration needs version TBD-DBU-1166: SDK release or later, as [DeepBook Predict SDK](/onchain-finance/deepbook/deepbook-predict-sdk#client) explains.

The distinction is easy to get wrong in the direction that fails silently rather than loudly. A call sent to an original ID reaches the version 1 code, which the version gate refuses for every gated function, because each network's watermark is 5. Only the few ungated calls, such as the builder-code setters and the fee claim, still run there. A type tag built from a call target, in turn, names a type that does not exist at all.

:::caution

Every identifier on this page belongs to one of the 2 current deployments. The current deployments supersede every earlier Testnet deployment, and the accounts, positions, and markets on those earlier deployments are not visible on the current ones, so ignore identifiers from them in local configuration files and scripts.

Both deployments went live on 2026-09-12. Read `read.markets()`, `read.pool()`, and the `ProtocolConfig` object rather than assuming either network's state.

:::

## Shared facts across both networks

Each `ExpiryMarket` is its own shared object, one per underlying and expiry. Market IDs are not deployment configuration: read them from `registry::expiry_market_id` onchain or from `read.markets()` at runtime. ## App authorization

The `deepbookCoreAccount` package declares the `account_data::DeepbookCoreAccountApp` type under its own package ID on each network. App authorization is live registry state rather than deployment configuration: a manifest's `externalAuthorizations` entry records only whether the authorization was in place when the deployment ran, and an admin grants or revokes it in a separate transaction afterward.

On both networks, the `AccountRegistry` authorizes `PredictApp`, `SessionsApp`, and `DeepbookCoreAccountApp`. That is live registry state, so read it with `account_registry::is_app_authorized<App>` rather than assuming it.

The DeepBook core registry is a separate authorization, and it is the one that gates the session spot wrappers. Sessions protocol version 4 also requires each pool to be on the `SessionsConfig` spot pool allowlist, as [Sessions](/onchain-finance/deepbook/deepbook-predict/contract-information/sessions#spot-wrappers) describes. Both DeepBook registries authorize `DeepbookCoreAccountApp`, Testnet's `0x7c256edbda983a2cd6f946655f4bf3f00a41043993781f8674a7046e8c0e11d1` and Mainnet's `0xaf16199a2dff736e9f07a845f23c5da6df6f756eddb631aed9d24a93efc4549d`, so the spot wrappers run on both networks. Both deployment manifests still record `externalAuthorizations.deepbookCoreAccount.authorized` as `false`, because neither registry had authorized the app when its deployment was verified. A manifest records only the state at deployment time, the authorization belongs to that registry's administrator rather than to Predict, and that administrator can grant or revoke it in a transaction of its own. Check it with `deepbook::registry::assert_app_is_authorized<DeepbookCoreAccountApp>`, which aborts when the app is not authorized. [Sessions](/onchain-finance/deepbook/deepbook-predict/contract-information/sessions) covers what that authorization gates.

## Units and constants

Predict mixes 2 scales, and confusing them is the fastest way to misprice a trade. Probabilities, prices, and rates are fixed-point integers, while coin amounts use the coin's own decimals. The units are identical on both networks:

| **Constant** | **Value** | **Applies to** |
| --- | --- | --- |
| Fixed-point scale | `1000000000` (1e9) | Probabilities, prices, tick sizes, and rates |
| Quote coin decimals | 6 | USDC amounts, premiums, fees, and payouts |
| PLP coin decimals | 6 | PLP share amounts |
| DEEP coin decimals | 6 | DEEP amounts |
| Position quantity decimals | 6 | Position quantities |
| Position lot size | `10000` | Position quantities, which must be whole multiples |
| Minimum premium | `1000000` | The premium of every mint, in USDC base units |
| Timestamp unit | Unix milliseconds | Onchain timestamps, expiries, and event windows |

A probability of `500000000` is 0.5. A price of `110000000000000` is 110,000.00. An amount of `1000000` is 1 USDC. A position quantity of `10000` is one lot, 0.01 contracts.

The lot size is the granularity of a quantity, not a tradable minimum. `strike_exposure_config::assert_mint_admission` rejects a mint whose premium falls below `1000000` base units, which is 1 USDC, with abort code `3`, `EPremiumBelowMinimum`, and on protocol version 4 the same rule refunds or refuses a queued order. The premium is the quantity multiplied by the quoted entry probability, and each market's `max_entry_probability` caps that probability, at `750000000` on both networks (TBD-DBU-1166: verify on Mainnet after the cutover). The smallest quantity such a market accepts is therefore about 1.34 contracts, and the floor rises as the strike moves further out of the money. Size a mint by the rule that predicts admission: `quantity` multiplied by the quoted `entryProbability` must reach 1 USDC. A quantity of 1 is below the floor on every live market.

Read every quantity that arrives as a JSON string with decimal or bigint tooling. Postgres `NUMERIC` columns serialize as strings, and `parseFloat` silently loses precision on them.

## Configuration

The values below are each network's current configuration. Configuration is mutable protocol state, so read the live values from `ProtocolConfig`, the `OrderDesk`, and `registry::cadence_configs` rather than pinning the ones below.

### Cadences

Cadence IDs index the registry's cadence table, which starts with 6 built-in cadences, IDs 0 to 5, and grows when an admin appends a length with `registry::add_cadence`. Read the periods with `registry::cadence_periods` rather than assuming 6. A cadence counts as enabled when its window size is greater than zero. An admin can enable or disable a cadence at any time, so read each network's enabled set from `registry::cadence_configs` rather than from this page. Both networks enable the 1m and 5m cadences, each with the same terms on both networks, and both register a 15m cadence at ID 6 and leave it disabled (TBD-DBU-1166: verify on Mainnet after the cutover):

| **ID** | **Name** | **Period (ms)** | **Enabled** | **Tick size** | **Admission tick size** | **Maximum expiry allocation** | **Initial expiry cash** | **Window size** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 1m | `60000` | Yes | `10000000` | `1000000000` | `500000000` | `500000000` | `2` |
| 1 | 5m | `300000` | Yes | `10000000` | `1000000000` | `1000000000` | `1000000000` | `2` |
| 2 | 1h | `3600000` | No | `0` | `0` | `0` | `0` | `0` |
| 3 | 1d | `86400000` | No | `0` | `0` | `0` | `0` | `0` |
| 4 | 1w | `604800000` | No | `0` | `0` | `0` | `0` | `0` |
| 5 | 1mo | `2592000000` | No | `0` | `0` | `0` | `0` | `0` |
| 6 | 15m | `900000` | No | `0` | `0` | `0` | `0` | `0` |

Read each column as follows:

- **Tick size:** The price-axis resolution, in fixed-point price units. Every enabled cadence uses `10000000`, which is 0.01 USD.
- **Admission tick size:** The coarser grid a finite position boundary must land on, also in fixed-point price units. Every enabled cadence uses `1000000000`, which is 1 USD, or every 100 ticks. A boundary tick must be a multiple of `admission_tick_size / tick_size` ticks.
- **Maximum expiry allocation:** The cadence cap on cash allocated to one expiry market, in USDC base units: 500 USDC on 1m and 1,000 USDC on 5m. This same value also scales the market's inventory-impact curve.
- **Initial expiry cash:** The cash the vault seeds a new market with, in USDC base units: 500 USDC on 1m and 1,000 USDC on 5m. From protocol version 5 an enabled cadence takes any positive value up to the maximum expiry allocation.
- **Window size:** How many expiries of this cadence can be live at once, so 2 markets of each enabled cadence are live at any time. Zero disables the cadence.

When 2 enabled cadences could create the same expiry, the one with the longer period owns it, so if the 15m cadence were enabled alongside 1m and 5m, quarter hours would go to 15m, other 5-minute marks to 5m, and every other minute to 1m.

The only finite boundary a market admits off its admission grid is its own reference tick. Read `admission_tick_size` from the market rather than assuming a grid, because cadence terms are mutable. Market creation on a disabled cadence aborts.

### Account and portfolio data

Account and position paths key on the canonical account ID, not on the shared `AccountWrapper` object ID and not on the owner address. An owner has 2 derived addresses, and only one of them answers here:

| **Endpoint** | **Use** |
| --- | --- |
| `GET /status` | Indexer freshness for the account pipelines |
| `GET /accounts/:account_id/portfolio` | Portfolio summary for one account |

| `GET /accounts/:account_id/activity` | Account activity history |
| `GET /apps` | App authorizations that the account registry records |

You have 2 routes to that ID:

- **Derive it from the owner address:** `new SessionsContract(getSessionsConfig(network)).deriveAccountId(owner)`, from the `@mysten/deepbook-v3/sessions` subpath, computes it offchain with no chain read. `client.predict` exposes only `wrapperIdFor`, which returns the wrapper, so the Predict client alone cannot produce this ID.
- **Read it off an event:** Every Predict order event carries the account ID in its `account_id` field, and `decode.createManager(result)` returns it as `accountId`.

:::caution

A wrapper ID passed where an account ID belongs fails silently. The services answer `200` with an empty array rather than an error, so a portfolio renders as empty and an automated redeemer reads it as nothing to close. Confirm the ID against an account you know holds positions before you trust an empty response.

:::

The wrapper ID stays correct onchain. Every Move call that takes the shared `AccountWrapper` object takes it, and `client.predict.wrapperIdFor(owner)` derives it. Only the read service paths key on the account ID. [Accounts and Custody](/onchain-finance/deepbook/deepbook-predict/contract-information/predict-manager) describes the 2 derived objects, and [Sessions](/onchain-finance/deepbook/deepbook-predict/contract-information/sessions) walks through deriving each one.

Take every path from the tables on this page rather than guessing at one. The plausible variants `/vault`, `/pool`, `/protocol-config`, and `/accounts/:account_id/apps` all return `404`.

### Freshness and pagination

```bash

```

Each response reports `status`, the latest onchain checkpoint, and every pipeline's indexed checkpoint and time lag. Treat a non-`OK` status, or an unexpectedly old pipeline you depend on, as incomplete recent data rather than as an empty application state.

Raw event pages need care, because they page differently from the named history feeds:

- The service orders raw event pages oldest-first by `(checkpoint_timestamp_ms, checkpoint, tx_index, event_index)`. Preserve that whole tuple when merging resources.
- The first page fixes a checkpoint snapshot. Continue with the opaque `page.next_cursor`, repeating every resource filter unchanged, until `page.has_next_page` is false.
- Raw event windows use `from_ms`, an inclusive lower bound, and `to_ms`, an exclusive upper bound, both in Unix milliseconds.
- Named history endpoints use `start_time` and `end_time` in Unix seconds instead, so never reuse one family's timestamps in the other.
- Named history feeds are generally newest-first, the opposite of raw event pages.
- An unknown identifier generally returns `null` components, an empty array, or a `null` point lookup rather than a `404`.

## Manage configuration across networks

The SDK carries both deployments' identifiers, so keep them in a single network-keyed record that you resolve once at startup rather than inlining an ID at a call site. [DeepBook Predict SDK](/onchain-finance/deepbook/deepbook-predict-sdk#configuration) shows that record, the startup deployment check, and which values change per deployment.

### Testnet and Mainnet differences

The 2 deployments run the same protocol versions, but they are separate deployments with separate configuration. What differs is:

- **Quote asset and funding:** Testnet quotes in a test coin you can request for free, and Testnet SUI is free. Mainnet quotes in native USDC, there is no faucet, and any top-up path that assumes free replenishment needs replacing.
- **SDK release:** Testnet works from version 2.10.0 of the SDK, and Mainnet needs version TBD-DBU-1166: SDK release or later, as [DeepBook Predict SDK](/onchain-finance/deepbook/deepbook-predict-sdk#client) explains.
- **Cadences and activity:** Each network's registry enables its own cadences, so read `registry::cadence_configs` rather than assuming either network's set. `read.markets()` lists live-and-unsettled markets, which includes an expired market nobody has settled, so check each entry's expiry before you quote against it.
- **Read services:** None exists for either current deployment as of 2026-09-14.
- **DeepBook core authorization:** Both deployment manifests record the DeepBook core registry as not having authorized `DeepbookCoreAccountApp`, yet both registries authorize it. Read the registry rather than the manifest before relying on the session spot wrappers, per [App authorization](#app-authorization).
- **Package version:** The networks have not upgraded in lockstep and need not. Compare protocol versions rather than publish counts, as [Publish count is not protocol version](#version-numbers) explains, and remember that an older call target keeps working only until the `ProtocolConfig` watermark passes it.

Structure your code so none of these become assumptions:

- **Lifecycle state:** Read it, do not infer it from time. Check `is_settled` or `try_settlement_price` on the market rather than deriving settlement from an expiry timestamp. A market settles when someone calls `try_settle` successfully, and the gap after expiry has no fixed duration.
- **Decimals and scale:** Take them from the configured deployment. An amount scaled by a hardcoded exponent silently misprices every mint.
- **Admission grid:** Read it from the market. Admission tick size is mutable protocol state.
- **Testnet timing:** Treat timing you measure on Testnet as an observation rather than a guarantee. Oracle update frequency and settlement latency are properties of the relayers, not of the contracts.

## Live onchain events

Stream events directly from a full node when a client needs them as they land, and back them with your own store for history. Predict emits its events from 4 modules under the Predict package: `config_events` for lifecycle and configuration, `order_events` for trading, `vault_events` for the pool and its queues, and `builder_code_events` for builder attribution. The queued-order events come from a fifth module, `queue_events`, in the `deepbook_predict_orders` package, so subscribe to both packages. The following table lists the ones an integrator subscribes to most often, not every event each module declares:

| **Event type** | **Emitted when** |
| --- | --- |
| `config_events::MarketCreated` | A lifecycle-cap holder creates and shares a new `ExpiryMarket` |
| `config_events::ReferenceTickSet` | A market records its reference tick |
| `config_events::MarketSettled` | A market settles, with `settlement_source` `0` for Pyth and `1` for Block Scholes |
| `config_events::ExpiryMarketMintPausedUpdated` | An admin pauses or unpauses minting on one market |
| `config_events::NoTradeWindowUpdated` | An admin changes `no_trade_window_ms` |
| `order_events::OrderMinted` | A queued mint fills |
| `order_events::LiveOrderRedeemed` | A queued early sell fills |
| `queue_events::OrderEnqueued` | A trader places a queued order |
| `queue_events::QueuedOrderFilled` | A queued order fills, beside the Predict order event |
| `queue_events::QueuedOrderRefunded` | The queue refunds a queued order, with a reason code |
| `queue_events::OpenRecordSettled` | The settlement walk pays an Open record |
| `config_events::FeeBandsUpdated` | An admin replaces the fee-band template, with the full table |
| `config_events::BuilderFeeCapUpdated` | An admin changes the builder fee cap |
| `config_events::CadenceAdded` | An admin appends a cadence to the registry's cadence table |
| `vault_events::SupplyRequested` | An account queues a liquidity supply request |
| `vault_events::SupplyFilled` | The flush fills a queued supply at its mark and mints PLP |
| `vault_events::WithdrawFilled` | The flush fills a queued withdrawal at its mark and burns PLP |
| `vault_events::RequestCancelled` | The owner cancels a queued request, or the flush refunds it |
| `vault_events::FlushExecuted` | The flush drains the liquidity queues at one frozen net asset value (NAV) |
| `vault_events::FlushRestarted` | A new pool valuation supersedes one that never finished |
| `builder_code_events::BuilderCodeCreated` | A caller creates a derived `BuilderCode` |
| `builder_code_events::BuilderCodeSet` | An account attaches or removes a builder code, which no fee reads from protocol version 5 |
| `builder_code_events::BuilderFeesClaimed` | A builder code owner claims accumulated builder fees |

The `SupplyFilled` and `WithdrawFilled` payloads name their quote amounts `usdc_amount`, `fee_usdc`, and `usdc_remaining`, and `WithdrawRequested` carries `min_usdc_out`.

### Stream events over gRPC

Stream Predict events with `SubscriptionService.SubscribeEvents`, filtering on the Predict package ID, and page the same events historically with `LedgerService.ListEvents` under an identical filter. Sui full nodes no longer serve the older WebSocket subscription API, so do not build on `sui_subscribeEvent`.

Subscribe to market creation and settlement on Testnet. The `PACKAGE` value is the Testnet `predict` original ID, because event type prefixes use the original ID rather than the call target. For Mainnet, swap in the Mainnet `predict` original ID, `0x89aea622e7bb3bdd598bde87dde40ee31c9eed4971b9546e23ec83de3c48bbba`, not its call target, and `fullnode.mainnet.sui.io:443`:

```shell
$ PACKAGE=0x59d71119e990573a738dd3ff9c4c7d28d6893af69c87c1a7f3a2e90e280ce2f4
$ ENDPOINT=fullnode.testnet.sui.io:443
$ METHOD=sui.rpc.v2.SubscriptionService/SubscribeEvents

$ grpcurl -format text -d "
read_mask {
  paths: \"event_type\"
  paths: \"json\"
  paths: \"sender\"
  paths: \"checkpoint\"
  paths: \"transaction_digest\"
  paths: \"transaction_index\"
  paths: \"event_index\"
}
filter {
  terms {
    literals {
      event_type {
        event_type: \"${PACKAGE}::config_events::MarketCreated\"
      }
    }
  }
  terms {
    literals {
      event_type {
        event_type: \"${PACKAGE}::config_events::MarketSettled\"
      }
    }
  }
}
" "$ENDPOINT" "$METHOD"
```

Swap the method for `sui.rpc.v2.LedgerService/ListEvents` to page the same events historically. The filter is disjunctive normal form, so the server ORs the `terms` blocks: the request above matches either event type and scopes both to one deployment.

Subscriptions begin at the current tip and accept no resume point, so recovering events missed during a disconnect always requires a `ListEvents` backfill. Those mechanics are the same for every gRPC event consumer, and the gRPC pages document them once, for all of them:

- [Subscribe to events with a filter](/develop/accessing-data/grpc/using-grpc#subscribe-to-events-with-a-filter) for the subscription call itself
- [Pagination with watermarks](/develop/accessing-data/grpc/using-grpc) for cursor semantics and the reasons a stream ends
- [Connection and buffer limits](/develop/accessing-data/grpc/using-grpc) for subscriber buffer sizes and slow-consumer eviction
- [Backfill and subscribe without gaps](/develop/accessing-data/grpc/grpc-migration-cookbook#backfill-and-subscribe-without-gaps) and [Reconnect a checkpoint stream](/develop/accessing-data/grpc/grpc-migration-cookbook#reconnect-a-checkpoint-stream) for the pairing pattern and reconnect backoff

`MarketSettled` is the correct trigger for an automated claim worker, because it fires when the contract actually records a settlement price rather than when a market expires. After settlement, the queue's own settlement walk pays every queued position into its owner's account with no claim at all, and `OpenRecordSettled` reports each payment. Protocol version 5 retires the settled redeem of positions held in accounts, so the worker has nothing to claim. A worker that also triggers the settlement walk should be idempotent: at-least-once delivery is a property of the backfill-and-subscribe pattern, so the same event can reach a handler twice after a reconnect.
