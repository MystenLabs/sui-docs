The position functions in the DeepBook Predict SDK place and follow queued orders, quote, open, close, and claim range positions on the immediate path, list the positions an account holds, and decode the receipt of each trade. [Predict](/onchain-finance/deepbook/deepbook-predict/contract-information/predict) explains the mechanics that these builders wrap.

The 2 networks trade differently. Testnet runs Predict protocol version 4, where every trade is a queued order, so use the functions under [Queued orders](#queued-orders) there. Mainnet runs protocol version 3 until its own cutover, where trades fill immediately, so use [Mint functions](#mint-functions) and [Close functions](#close-functions) there. `read.executionMode()` tells your app which path a network is on, so it can switch at the cutover without a redeploy.

Every function is a member of `client.predict`, which [DeepBook Predict SDK](/onchain-finance/deepbook/deepbook-predict-sdk#client) shows how to register. Each builder and quote that targets a market takes the market as a [market descriptor](/onchain-finance/deepbook/deepbook-predict-sdk/markets): an object that names the market by its `underlying`, `expiryMs`, and optional `marketId`, plus the strike, as a binary or range position, where the call needs one. The function then reads the chain to resolve the market object and caches it per client, so those functions are asynchronous. The SDK takes and returns amounts as decimal USDC values and converts them to 6-decimal base units; see [Units](/onchain-finance/deepbook/deepbook-predict-sdk#units).

:::caution

The immediate position builders default to uncapped slippage. `tx.mint` sends `U64_MAX` for `maxCost` or `maxProbability` when you omit it, `tx.mintAmount` sends `U64_MAX` when you omit `maxCost`, and `tx.redeem` always sends `0` for both close-side floors. Quote immediately before each trade, derive every mint cap from the quote, and use a builder that takes floors when a close needs them. [`tx.mint`](#mint), [`tx.mintAmount`](#mint-amount), and [`tx.redeem`](#redeem) describe each default in full.

`tx.mintCost` is the exception: its `spend` is the sizing input, so the debit cannot exceed it and there is no cap to forget. Its `minQuantity` is still yours to set, because a `0` floor accepts however few contracts the budget buys after an adverse move.

:::

## Queued orders {#queued-orders}

From Predict protocol version 4, a mint or an early sell is a queued order. You place it with its limits and its money, it waits in its market's queue until Pyth Lazer publishes its signed price for the order's price instant, τ, about 800 ms after placement on Testnet, and a keeper or any other caller then fills it at that price or refunds it. Version 2.7.0 of the SDK adds the queued path to `client.predict` and records Testnet's delayed-execution deployment. Its Mainnet configuration does not record one yet, so the queued functions throw `PredictInputError` there until the SDK syncs the Mainnet rollout, unless you pass a `config` that sets `packages.predictDelayedExecution`, `packages.predictOrders`, `objects.orderDesk`, and `objects.queueRegistry`.

A queued order differs from an immediate trade in 4 ways:

- **Placement and fill are separate transactions.** The enqueue debits the order's budget and a flat order fee into the order's escrow and returns a record ID. The fill lands about a second later in another caller's transaction. Unused budget comes back at the fill.
- **The slippage is cents per contract.** `slippageCents` bounds how far the all-in price per `$1` of payout might rise above the quote's price without the fee subsidy, so `slippageCents: 10` lets a contract quoted at 42 cents before the subsidy fill at up to 52 cents, fees included. It is never a percentage. `'auto'` sizes it from a model of the price's movement until τ.
- **A filled mint is an Open record.** It stays in the market's queue rather than entering the account, so `read.positions` does not list it. Follow it by its record ID, sell it with another queued order, and let the queue's settlement walk pay it after expiry.
- **A refund is a normal outcome.** An order that misses its limits at τ, or that the market cannot cover, gets a refund with a reason code, and a refund for the order's own limits or for admission keeps the order fee.

### `read.executionMode` {#execution-mode}

Use `read.executionMode` to find out which trade path a network is on. It returns a `Promise<ExecutionMode>`, one of `'immediate'`, `'awaiting-cutover'`, `'delayed'`, `'unsupported'`, or `'retired'`. It reads the `ProtocolConfig` version watermark and checks whether the configuration records delayed execution. `'retired'` means a later upgrade raised a version floor above the code this SDK release calls, so upgrade the SDK.

### `read.planMint` {#plan-mint}

Use `read.planMint` to build a purchase form's state and the limits a queued mint carries. It returns a `Promise<MintPlan>`. It quotes the order at the current price, for a visitor without an account too, turns the slippage into the enqueue's limits, and runs the enqueue builder's preflight, so `accepting` is `false`, with a typed `refusal`, when the order would be refused now. The preflight covers the queue gates, the balance, and the order's limits, not every onchain check.

It takes these parameters:

- `owner`: The address that owns the account.
- `m`: The market and strike, as a binary or range market descriptor. Snap a numeric strike onto the admission grid with `snapStrike`, and prefer a strike near the money, because admission refuses an entry probability outside the market's band.
- `opts`: A `PlanMintOptions` object: either `amount`, an all-in spend in USDC that includes the order fee unless `orderFee` is `'exclusive'`, or `quantity`, an exact payout, plus `slippageCents`.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="26f6fdfae9604d08f27ebe150f1533fb95800422" lines="2459-2463" />

A `MintPlan` carries `potentialPayout`, `minPayout` at the worst price, `payoutMultiple`, `pricePerContract`, `worstPricePerContract`, `orderFee`, `budget`, `totalDebit`, the account's `balance`, `maxNow`, the largest amount the market and the balance take now, a `timing` preview of τ and the deadline, and the `order` the plan builds. The plan sizes the limits from the price without the fee subsidy, because placement checks the order without it. `planMint` throws a `PredictPreflightError` with code `entry-band` for a strike outside the band, `min-premium` for a budget that buys less than 1 USDC of premium, and `past-cutoff` for a market past its expiry, where the chain has no live price to quote. Near the cutoff, the plan's `refusal` is `past-cutoff` instead, and the preview runs on the device clock, so the chain can still refuse an order placed in the last seconds.

### `tx.enqueuePlan` {#enqueue-plan}

Use `tx.enqueuePlan` to queue the order a plan describes. It returns a `Promise<QueuedOrderPlan>`, the `transaction` and a `preview` of τ, the deadline, the escrow, the order fee, and whether a sell needs funding. Pass the descriptor you planned the mint with, or the coordinates a sell plan took. It reads the gates and the balance again and throws a `PredictPreflightError` for a refused plan or a balance that now escrows less than the plan's budget, and a `PredictInputError` for an order fee that rose since the plan or for another owner, market, strike, or record than the plan's target. Each enqueue it builds starts with a check that aborts the transaction if the order desk's fee rose between building and execution.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="26f6fdfae9604d08f27ebe150f1533fb95800422" lines="1934-1938" />

The lower-level builders `tx.enqueueMint`, `tx.enqueueMintAmount`, `tx.enqueueMintCost`, and `tx.enqueueSell` take the limits directly, in SDK units, and run the same preflight. Every queued mint needs a finite cost cap, because the chain aborts a zero or unlimited `max_cost` with `EMintCostCapRequired`.

The preflight codes are `not-live`, `no-queue`, `retired`, `paused`, `stuck`, `past-cutoff`, `queue-full`, `account-cap`, `fee`, `market-cash`, `min-premium`, `entry-band`, `cost-above-payout`, `below-min-sell`, `record-not-open`, and `not-record-owner`. `fee` means the balance cannot cover the order fee, or the plan's whole debit, so prompt a deposit. Some checks run only onchain at placement, such as the market's SVI age and room in the payout tree for a new strike, and those abort the transaction rather than raising a preflight code. `describePredictError` turns any of these aborts into readable text.

### `decode.enqueue` {#decode-enqueue}

Use `decode.enqueue` to read the record ID, τ, deadline, escrow, and order fee from the enqueue's `OrderEnqueued` event. It throws unless the result holds exactly one, and `decode.enqueues` returns every enqueue in a batched transaction. Persist `recordId`: it is the handle for everything that follows, and nothing onchain lists an account's queue records for you.

### `read.waitForOutcome`, `read.order`, and `read.orders` {#wait-for-outcome}

Use `read.waitForOutcome` to poll a record until it is filled, refunded, or closed. It returns a `Promise<QueuedOrderOutcome>` whose `outcome` is `'filled'`, `'refunded'`, `'closed'`, `'gone'`, or `'timeout'`, with the record's `order` view. It polls every 250 ms by default for up to 30 seconds, and keeps polling a record the full node does not show yet. After expiry, `'gone'` for a filled record means the queue paid it out and deleted it, not that you lost the order.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="26f6fdfae9604d08f27ebe150f1533fb95800422" lines="2872-2876" />

`read.order(m, recordId)` and `read.orders(m, recordIds)` read records without waiting. Each record's `view.state` is `'placed'`, `'priced'`, `'refunding'`, `'filled'`, `'refunded'`, or `'closed'`. A filled record's `view.position` carries the packed `orderId` and the held quantity, and `view.sellable` reports whether you can sell it now. A keeper that commits a price and fills in one transaction moves an order from `'placed'` straight to `'filled'`, so do not count on seeing `'priced'`.

### `read.planSell` {#plan-sell}

Use `read.planSell` to plan an early sell of an Open record. It returns a `Promise<SellPlan>` with the `proceeds` at the current price, `net` after the order fee, the `minProceeds` and `minNet` floors at the worst price the slippage allows, and the `order` for `tx.enqueuePlan`. It throws `PredictPreflightError` with code `record-not-open` for a record that is not Open. A sell pays the order fee whatever it returns, so `net` is negative for a sell worth less than the fee. `read.quoteSell` returns the same quote without the plan.

It takes these parameters:

- `owner`: The address that owns the account and the record.
- `m`: The market's `underlying`, `expiryMs`, and optional `marketId`.
- `opts`: A `PlanSellOptions` object with the `recordId`, the payout `quantity` to sell, and `slippageCents`.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="26f6fdfae9604d08f27ebe150f1533fb95800422" lines="2762-2766" />

The whole position moves into the sell's own record, so after a sell, including a partial one, the remainder lives under the sell's record ID. A sell the market cannot cover at the fill gets a refund, and the position returns to an Open record. When a sell's cash need is above the market's spare cash, `tx.enqueueSell` appends `rebalance_expiry_cash` after the enqueue by default, and its `fundMarket` option controls that.

### `tx.refund`, `tx.claimParked`, and `tx.payOpen` {#refund}

Keepers refund an order still unfinished 5 seconds after its τ, so these builders are recovery paths, and each is permissionless:

- **`tx.refund(m, { maxOrders })`** refunds the market's orders past their deadline. Offer it only when a record's `view.canRequestRefund` is `true`, and never prepend it to other transactions. It needs no account and works during the emergency freeze.
- **`tx.claimParked(m, recordId)`** sends a finished record's parked USDC, a refund or change its receive address could not take while denied, to that address once it is clear.
- **`tx.payOpen(m, recordId)`** pays a settled Open record that the settlement walk skipped.

### `read.settlement` and `cost.settledPayout` {#settlement}

After expiry, `read.market`, `read.price`, and the quotes abort with `ELivePricingExpired`, and the queue's keeper settles the market, pays each Open record, and deletes it, usually within seconds. `read.settlement(m)` still works: it returns the settlement price as a decimal and as `settlementPriceRaw`, with `tickSizeRaw`, or `settled: false` until a keeper settles. Pass the stored `orderId` with those 2 raw values to `cost.settledPayout` for what the position is owed at that price, in raw USDC. That is a calculation, not proof of payment: the payout walk's `OpenRecordSettled` event is the payment to the account's receive address, and a record the walk skipped, because the market was short of cash or the address was denied, emits `OpenRecordPayoutSkipped` instead and stays Open until `tx.payOpen` pays it. `read.pendingFunds(owner)` reports refunds, sell proceeds, and payouts that reached the account but are not settled into its stored balance yet, which `read.balance` already counts.

### Queue decoders {#queue-decoders}

`decode.queueEvents` returns every queue event in a result, tagged and in chain order, and `queue.reduceOrderEvents` folds a stream of them into the same order states the reads return, for an indexer or an event feed. The typed decoders are `decode.cohortCommits`, `decode.queuedFills`, `decode.queuedRefunds`, `decode.openRecordPayouts`, `decode.marketPayoutsCompleted`, `decode.recordFunds`, and `decode.queueOps`. They match the order-flow package's events against its original ID, and `decode.queuedFills` sits beside `decode.mints` and `decode.redeems`, which still read the Predict `OrderMinted` and `LiveOrderRedeemed` that every fill emits.

## Mint functions {#mint-functions}

The functions in this section and the next are the immediate path, which runs on a network before its delayed-execution cutover. From protocol version 4 the builders `tx.mint`, `tx.mintAmount`, `tx.mintCost`, and `tx.redeem` abort with `EDelayedExecutionRequired`, and version 2.7.0 marks them and `read.quoteRedeem` deprecated. `read.quoteMint` and `read.quoteMintCost` keep working there: on a network whose configuration records delayed execution, they read the protocol version 4 quotes and preview a queued fill, with the order fee reported separately. `tx.claimSettled` keeps working on both for a position held in the account.

Minting opens a position at the live price, and the SDK offers 3 sizing shapes: `tx.mint` fixes the payout quantity, `tx.mintAmount` fixes the premium budget, and `tx.mintCost` fixes the all-in budget. Every mint builder checks each numeric strike against the market's tick and admission grids, then builds 3 commands: load a fresh pricer from the oracle feeds, generate the account authorization from the sender, and call the Move mint function. Every mint is also subject to 3 limits:

- **Lot size:** A payout quantity moves in whole lots of 0.01 USDC. `tx.mint` and `read.quoteMint` throw `PredictInputError` for a `quantity` that is not a whole lot, before they build anything. The budget builders round the fill down to a lot themselves.
- **Premium floor:** The contract rejects a mint whose premium, `quantity` multiplied by the quoted entry probability, falls below 1 USDC, with `EPremiumBelowMinimum`. The lot is the granularity, not the minimum: on a Mainnet market with a `0.75` maximum entry probability no strike clears the floor below about 1.34 contracts, and a strike quoting near a 50 percent chance needs roughly 2. See [mint admission errors](/onchain-finance/deepbook/deepbook-predict/contract-information/predict).
- **No-trade window:** Inside the [no-trade window](/onchain-finance/deepbook/deepbook-predict/contract-information/predict), the last 10 seconds before expiry on Mainnet as of 2026-10-13, a mint aborts with `ETradeWindowClosed`. The SDK quote runs the same gate, but a quote taken just before the window opens can succeed while the mint that follows aborts.

### `read.quoteMint` {#quote-mint}

Use `read.quoteMint` to price a mint exactly before you send it. It returns a `Promise<MintQuote>`. It simulates the same mint `tx.mint` builds, with the owner as sender, against the owner's real account and the real fee path, so it throws the same typed errors the mint would, including insufficient balance, and serves as a preflight check. It sends only the options you pass. Called with `{ quantity }`, the dry run carries no slippage cap, because a cap only gates a mint through an abort and never changes its receipt. An options object that also holds `maxCost` or `maxProbability` passes them through, and the quote then aborts on a cap exactly as the mint would.

The owner needs a funded account for the quote to succeed. The Move `expiry_market::quote_mint` is a different call that prices only and checks no account and no slippage cap; see [Quote a mint](/onchain-finance/deepbook/deepbook-predict/contract-information/predict).

It takes these parameters:

- `owner`: The address that owns the account. The simulation runs with this address as sender.
- `m`: The market and strike, as a binary or range market descriptor.
- `opts`: An object with the payout `quantity` to price, as a whole lot of 0.01 USDC.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="56d51645cd231010e39d96dd23583056c5266426" lines="912-916" />

`MintQuote` carries these fields:

| **Field** | **Meaning** |
| --- | --- |
| `entryProbability` | Fill price between 0 and 1 per 1 USDC of payout, which `maxProbability` caps |
| `premium` | Premium alone, before fees |
| `fees` | Exact fee breakdown by component |
| `cost` | All-in account debit, which `maxCost` caps |
| `quantity` | Payout quantity the quote priced |
| `raw` | Exact `bigint` amounts for `premium`, `cost`, `quantity`, and `entryProbability` |
| `feesExact` | Always `true`, because the fees come from the real mint code path |

`fees` breaks the debit into these components:

- `trading`: The trading fee before the sponsor subsidy, summed over the finite boundaries of the range.
- `subsidy`: The sponsor-funded part of the trading fee, which you do not pay.
- `builder`: The builder add-on, 0 when the account carries no builder code.
- `penalty`: The congestion surcharge.
- `referral`: The portion of the trading fee and congestion surcharge that the protocol routes to a referrer. It is already inside those amounts, not an extra debit, and it is 0 unless you created the account with a referrer; see [Referrals](/onchain-finance/deepbook/deepbook-predict/design).
- `inventoryImpact`: The inventory-impact charge, a separate charge that `cost` includes.

`cost` is `premium + (trading - subsidy) + builder + penalty + inventoryImpact`, the same total the contract withdraws, so pass `cost` plus a buffer as `maxCost`, never `premium`. `referral` has no term of its own in that sum because it is already counted inside `trading` and `penalty`. [Design](/onchain-finance/deepbook/deepbook-predict/design) explains each fee component. `raw` carries exact amounts for `premium`, `cost`, `quantity`, and `entryProbability` but no fee amounts, so read exact fees from `decode.mint(result).raw`, which carries every fee component as an exact `bigint`, after execution.

### `tx.mint` {#mint}

Use `tx.mint` to mint a position of an exact payout quantity, the SDK form of `mint_exact_quantity`. It returns a `Promise<Transaction>`. When you omit `maxCost` or `maxProbability`, the SDK sends `U64_MAX` for it, which caps nothing. The premium is `quantity` multiplied by the entry probability, which the contract caps below 1, so the premium alone cannot exceed `quantity` even uncapped. The protocol charges fees on top of the premium, so `maxCost` is what bounds the total debit, and `maxProbability` bounds the fill price.

A mint whose all-in cost would exceed `quantity` aborts with `EMintCostAboveMaxPayout`. Read the new order ID from `decode.mint(result).orderId` after execution. For a complete quote-then-mint flow, see the [quote-and-mint sample](#example-mint).

It takes these parameters:

- `owner`: The address that owns the account. The same address must sign, because the transaction generates the account authorization from its sender.
- `m`: The market and strike, as a binary or range market descriptor.
- `opts`: A `MintOptions` object with 3 fields:
  - `quantity`: The payout quantity in USDC, which is the position's maximum payout at 1 USDC per contract. It must be a whole lot of 0.01 USDC.
  - `maxCost`: The optional ceiling on the all-in account debit, in USDC. Derive it from the quote's `cost`, and round it to at most 6 decimals, because a finer value throws `PredictInputError`.
  - `maxProbability`: The optional ceiling on the quoted per-contract probability before fees, between 0 and 1. Derive it from the quote's `entryProbability` and round it to at most 9 decimals, because the SDK throws `PredictInputError` for more.

### `tx.mintAmount` {#mint-amount}

Use `tx.mintAmount` to mint by premium budget rather than by payout, the SDK form of `mint_exact_amount`. It returns a `Promise<Transaction>`. The contract caps `spend` at the account's available USDC, mints the largest lot-rounded quantity whose premium fits, and charges fees on top of `spend`, so `maxCost` is the only bound on the whole withdrawal. When you omit `maxCost`, the SDK sends `U64_MAX`. The contract's `EMintCostCapRequired` guard fires only on a cap of exactly 0, which the SDK already rejects, so nothing bounds the debit of a mint without `maxCost`.

It takes these parameters:

- `owner`: The address that owns the account and signs the transaction.
- `m`: The market and strike, as a binary or range market descriptor.
- `opts`: A `MintAmountOptions` object with 3 fields:
  - `spend`: The premium budget in USDC, which is the most premium the mint pays.
  - `minQuantity`: The smallest payout quantity you accept. The contract aborts when the budget buys less. It need not be a whole lot, because the contract compares it against a quantity it has already rounded down to a lot.
  - `maxCost`: The optional ceiling on the whole withdrawal, premium plus fees, in USDC. The SDK throws `PredictInputError` for a value at or below 0.

`tx.mintAmount` takes no `maxProbability`, because `minQuantity` against a fixed budget already bounds the price per contract. `read.quoteMint` prices an exact quantity only, so no SDK quote dry-runs this builder, and `decode.mint(result).quantity` reports the quantity the contract actually minted. The following snippet spends at most 5 USDC of premium, accepts no fewer than 8 contracts, and caps the whole withdrawal at 5.25 USDC. It assumes `client`, `owner`, and `descriptor` from the samples under [Examples](#examples):

```ts
import type { MintAmountOptions } from '@mysten/deepbook-v3/predict';

const opts: MintAmountOptions = { spend: 5, minQuantity: 8, maxCost: 5.25 };
const tx = await client.predict.tx.mintAmount(owner, descriptor, opts);
```

### `read.quoteMintCost` {#quote-mint-cost}

Use `read.quoteMintCost` to see what an all-in budget buys before you spend it. It returns a `Promise<MintQuote>`. It simulates the same transaction `tx.mintCost` builds, with the owner as sender, against the owner's real account and the real fee path, so it runs the chain's own budget search and reports the fill that search selects. Read `quantity` from it to set the `minQuantity` floor on the mint that follows, and `cost` to see how much of the budget the fill actually spends.

It takes the same 3 arguments as `tx.mintCost`, described in the next section.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="56d51645cd231010e39d96dd23583056c5266426" lines="922-926" />

The quote does not preflight the expiry's cash backing or its exposure-index capacity, so a mint can still abort where its quote succeeded. Like the mint, it needs Predict package version 2.

### `tx.mintCost` {#mint-cost}

Use `tx.mintCost` to mint inside an all-in budget, the SDK form of `mint_exact_cost`. It returns a `Promise<Transaction>`.

:::info

`tx.mintCost` and `read.quoteMintCost` call an entrypoint that arrived in `predict` package version 2, which Mainnet runs. The `tx.mintCost` code snippet in this section still carries the SDK's own comment saying Testnet only, which the Mainnet upgrade has since overtaken. On Testnet, version 2.7.0 of `read.quoteMintCost` reads the protocol version 4 quote instead and previews a queued fill, and `tx.mintCost` aborts there.

:::

The difference from `tx.mintAmount` is what the budget covers. `spend` on `tx.mintAmount` is a **premium** budget, and the trading fee, builder add-on, congestion surcharge, and inventory-impact charge land on top of it, which is why that builder needs a separate `maxCost`. `spend` on `tx.mintCost` is the **whole withdrawal**. The contract caps it at the account's available USDC, then sizes the largest lot-rounded fill whose complete debit fits, probing the same cost computation it charges against fee and book state at execution. The debit therefore cannot exceed `spend`, and you need no fee estimate and no padding against fee state moving between the quote and execution.

It takes these parameters:

- `owner`: The address that owns the account and signs the transaction.
- `m`: The market and strike, as a binary or range market descriptor.
- `opts`: A `MintCostOptions` object with 2 fields:
  - `spend`: The all-in budget in USDC, fees included. The contract caps it at the account's available balance.
  - `minQuantity`: The smallest payout quantity you accept, in USDC. This is the builder's slippage guard, and `0` disables it.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="56d51645cd231010e39d96dd23583056c5266426" lines="696-696" />

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="56d51645cd231010e39d96dd23583056c5266426" lines="136-142" />

`minQuantity` replaces both caps the other builders take. The spend is fixed, so an adverse move in price, congestion surcharge, sponsor subsidy, or inventory impact between building the transaction and executing it arrives as fewer contracts rather than a larger debit, and one floor on the fill catches all of them: a fill below it aborts with `EMintQuantityBelowMin`. It bounds the all-in price per contract at `spend / minQuantity`, which is why this builder takes no `maxProbability` and no `maxCost`.

Three limits qualify the fill:

- **The one-lot remainder holds only when the budget binds.** Where the budget is what limits the fill, less than the incremental all-in cost of one more lot goes unspent. A fill limited by something else can leave much more.
- **The maximum-payout bound can step the fill down.** The marginal inventory-impact rate rises with liability, so the largest fill a budget could pay for is sometimes one that would cost more than its own maximum payout. Sizing then falls back to a smaller fill, and that fallback is conservative: it can miss a larger admissible fill, or abort on `minQuantity` or the minimum premium where another size would have succeeded. A market where no size clears the bound aborts with `EMintCostAboveMaxPayout`.
- **Backing is not a sizing input.** Insufficient expiry cash backing aborts the mint rather than shrinking it.

Read the quantity the contract actually minted from `decode.mint(result).quantity`. The following snippet spends at most 25 USDC in total, fees included, and rejects a fill under 30 contracts. It assumes `client`, `owner`, and `descriptor` from the samples under [Examples](#examples):

```ts
import type { MintCostOptions } from '@mysten/deepbook-v3/predict';

const preview = await client.predict.read.quoteMintCost(owner, descriptor, {
	spend: 25,
	minQuantity: 0,
});

// Take the floor from the quote, then leave a little room for the price to move.
const opts: MintCostOptions = { spend: 25, minQuantity: preview.quantity * 0.99 };
const tx = await client.predict.tx.mintCost(owner, descriptor, opts);
```

For a preview that costs no chain call at all, [Predict Cost SDK](/onchain-finance/deepbook/deepbook-predict-sdk/cost) runs the same budget search locally from a pricer snapshot.

## Close functions {#close-functions}

On the immediate path, closing follows either of 2 paths, depending on whether the market has settled. Before settlement, `tx.redeem` closes all or part of a position at the live price. After settlement, `tx.claimSettled` claims the fixed payout. An order ID is unique only inside a single market, so both builders take the market along with the order ID.

### `read.quoteRedeem` {#quote-redeem}

Use `read.quoteRedeem` to price a live close exactly before you send it. It returns a `Promise<RedeemQuote>`. It simulates the same transaction `tx.redeem` builds, with the owner as sender, so it throws the same typed errors the close would. `tx.redeem` sends no floors, so the quote is the only price check a facade close gets: quote immediately before you send, and treat the proceeds as an estimate.

It takes these parameters:

- `owner`: The address that owns the account. The simulation runs with this address as sender.
- `m`: The market descriptor you minted the position with.
- `opts`: A `CloseOptions` object with the position's `orderId` and the `quantity` to close.

<ImportContent source="packages/deepbook-v3/src/predict/client.ts" mode="code" org="MystenLabs" repo="ts-sdks" branch="56d51645cd231010e39d96dd23583056c5266426" lines="931-935" />

`RedeemQuote` carries these fields:

| **Field** | **Meaning** |
| --- | --- |
| `proceeds` | Net USDC that the close credits to the account |
| `gross` | Close value before fees |
| `fees` | Exact `trading`, `builder`, `penalty`, and `inventoryImpactRebate` amounts |
| `quantityClosed` | Payout quantity the close removes |
| `remaining` | Payout quantity that stays open after the close |
| `raw` | Exact `bigint` amounts for `proceeds`, `gross`, and `quantityClosed` |
| `feesExact` | Always `true`, because the fees come from the real redeem code path |

`proceeds` is `gross + inventoryImpactRebate - trading - builder - penalty`, the same net amount the contract checks `min_proceeds` against.

### `tx.redeem` {#redeem}

Use `tx.redeem` to close all or part of a live position at the current price, the SDK form of `redeem_live`. It returns a `Promise<Transaction>`. It sends `0` for both `min_probability` and `min_proceeds` on every call, and `CloseOptions` has no field to raise them, so the close accepts whatever price the pricer returns at execution.

The floors are reachable through 2 other routes. The `/sessions` subpath's `redeemLive` builder takes `minProbability` and `minProceeds` for a close that a session key signs; see [slippage bounds](/onchain-finance/deepbook/deepbook-predict-sdk/sessions). For an owner-signed close, build a `moveCall` against `redeem_live` yourself from the [composition exports](/onchain-finance/deepbook/deepbook-predict-sdk#compose) and the signature under [Redeem a position](/onchain-finance/deepbook/deepbook-predict/contract-information/predict).

A partial close retires the order ID and issues a replacement for the remaining quantity, which `decode.redeem(result).replacementOrderId` reports. A live close in the same timestamp as its mint aborts with `EMintRedeemSameTimestamp`, and a live close inside the no-trade window aborts with `ETradeWindowClosed`. After expiry, wait for settlement and claim instead.

It takes these parameters:

- `owner`: The address that owns the account and signs the transaction.
- `m`: The market descriptor you minted the position with. The SDK reads only its `underlying`, `expiryMs`, and optional `marketId`, because the order ID identifies the position.
- `opts`: A `CloseOptions` object with 2 fields:
  - `orderId`: The position's current order ID, as a `bigint`.
  - `quantity`: The payout quantity to close, as a whole lot of 0.01 USDC. The SDK throws `PredictInputError` for a quantity that is not a whole lot.

### `tx.claimSettled` {#claim-settled}

Use `tx.claimSettled` to claim a position whose market has settled, the SDK form of the owner-authorized `redeem_settled`. It works on both networks for a position held in the account, including one minted before Testnet's cutover. It does not pay a queued fill, which the queue's settlement walk pays instead. It returns a `Promise<Transaction>`. A settled claim always closes the order in full, so the builder takes no quantity, and the order ID identifies the position, so it takes no side or strike. It loads no pricer, because settlement has already fixed the price. The payout is the full quantity when the settlement price lands inside the position's range and 0 otherwise.

Before settlement the claim aborts with `EMarketNotSettled`, and expiry alone does not settle a market. Settlement runs through the permissionless `expiry_market::try_settle`, which the SDK does not build; see [Settle a market](/onchain-finance/deepbook/deepbook-predict/contract-information/predict). The no-trade window does not apply to a claim. The SDK also builds no `redeem_settled_permissionless`, the path that lets any address claim on a holder's behalf.

It takes these parameters:

- `owner`: The address that owns the account and signs the transaction.
- `m`: The market's `underlying`, `expiryMs`, and optional `marketId`.
- `opts`: An object with the position's `orderId`.

## Position reads {#position-reads}

The SDK reads positions straight from the account's onchain position table, so neither read needs an indexer. The fastest path is to persist the order ID from each mint receipt and replace it after each partial close; use these reads to recover a lost ID or to validate a stored one.

### `read.positions` {#positions}

Use `read.positions` to list every open position an owner's account holds. A queued fill is not one of them: it is an Open record in the market's queue, which `read.order` reads. It returns a `Promise<OpenPosition[]>`, an entry for each position, each carrying the `marketId` and `orderId` that `tx.redeem`, `tx.claimSettled`, and `read.hasPosition` take. It returns an empty array for an owner with no Predict account or no Predict positions.

The SDK caches the account and table IDs per owner once the table exists, so later reads cost 1 request per page of positions. A transport failure throws rather than reading as an empty list, and a table that still has entries after 10 pages throws a plain `Error`. `OpenPosition` carries no underlying or expiry, so supply those yourself when you build the descriptor for a close.

It takes this parameter:

- `owner`: The address that owns the account.

## Receipt decoders {#decode}

The receipt decoders turn an executed transaction's events into typed receipts, with no network call. Include events when you execute the transaction, and pass the result. Without events, a singular decoder throws `PredictInputError` because it finds no matching event, and a plural decoder returns an empty array. A decoder also throws `PredictInputError` when a matching event carries no Binary Canonical Serialization (BCS) payload. Each singular decoder throws `PredictInputError` unless the result holds exactly 1 matching event, and each plural decoder returns every matching receipt in event order, for a transaction that batches several trades. [DeepBook Predict SDK](/onchain-finance/deepbook/deepbook-predict-sdk#decode) covers how the decoders read events.

### `decode.mint` and `decode.mints` {#decode-mint}

Use `decode.mint` to read the receipt of a mint, and `decode.mints` to read every mint in a single transaction. Each decodes the [`OrderMinted`](/onchain-finance/deepbook/deepbook-predict/contract-information/predict) event and returns a `MintReceipt`, or an array of them. Persist `orderId`, because closing or claiming the position needs it with the market ID. `positionRootId` stays stable across partial-close replacements, `quantity` is the quantity the contract actually minted, which it rounds down to a lot for `tx.mintAmount`, and `raw` carries every fee component as an exact `bigint`.

It takes this parameter:

- `r`: The executed transaction result, including its events.

### `decode.redeem` and `decode.redeems` {#decode-redeem}

Use `decode.redeem` to read the receipt of a live close, and `decode.redeems` to read every live close in a single transaction. Each decodes the [`LiveOrderRedeemed`](/onchain-finance/deepbook/deepbook-predict/contract-information/predict) event and returns a `RedeemReceipt`, or an array of them. After a partial close, `replacementOrderId` carries the order ID of the remaining quantity: store it in place of the old one, or the next close targets an order that no longer exists. It is `null` after a full close, and `proceeds` is the net amount the close credits, which the SDK computes the same way as in `RedeemQuote`.

It takes this parameter:

- `r`: The executed transaction result, including its events.

## Examples {#examples}

The following samples live in the `examples/deepbook-predict` package, which type-checks against version 2.7.0 of `@mysten/deepbook-v3`. They show the immediate path, so they run only on a network before its delayed-execution cutover, and [Queued-order examples](#queued-examples) shows the queued path. None of them signs a transaction: every builder returns an unsigned `Transaction`, and the SDK never holds keys.

On the immediate path, a complete mint-then-close flow runs in this order:

1. Call `read.quoteMint` immediately before the trade.
2. Build the mint with `tx.mint`, passing a `maxCost` and a `maxProbability` derived from the quote.
3. Sign and execute the transaction with events included, then persist `decode.mint(result).orderId`.
4. Before settlement, call `read.quoteRedeem` and close with `tx.redeem`. After a partial close, store `decode.redeem(result).replacementOrderId` in place of the old order ID.
5. After the market settles, claim with `tx.claimSettled` and read the `payout` from `decode.claim(result)`.
